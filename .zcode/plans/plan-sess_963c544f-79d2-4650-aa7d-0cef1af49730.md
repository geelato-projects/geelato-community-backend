# 灰度发布方案（OpenResty 分流 + SpringBoot 染色 + Redis JSON 规则）

## 架构

```
浏览器
   │ (首次无Cookie → OpenResty 默认走老后端；携Cookie → 按tag路由)
   ▼
OpenResty (纯路由, 零业务逻辑, 不查Redis)
   │ 读 gl_traffic_tag Cookie: 值=gray → 新后端; 否则 → 老后端
   │ 透传 X-Gl-Traffic-Tag 头
   ├──────────────► 老 SpringBoot (默认)
   └──────────────► 新 SpringBoot (gray)
                      │ 现有 DefaultSecurityInterceptor → TrafficTagResolver
                      │   无Cookie时 → JsonRuleTrafficTagStrategy.resolveTag(user)
                      │     └ 读 Redis JSON 规则 → 按身份匹配 → 返回 gray/default
                      │ 登录后 applyAfterAuthenticated(user) 用真实身份校准
                      │ 写裸Cookie + ThreadLocal/MDC
                      ▼
                   Redis  (key: geelato:gray:rules  → JSON 规则串)
                      ▲ 运维直接 SET 写JSON + 调 /api/gray-rules/reload 刷内存
```

**职责**：SpringBoot 染色(复用现有链路) / OpenResty 只读Cookie路由 / Redis 存 JSON 规则 / 不建实体、不建表、仅 reload 接口、**不签名**。

**关于签名**：`TrafficColoringProperties.signingEnabled` 默认值改为 `false`。Cookie 为裸字符串（`gl_traffic_tag=gray`），新老后端读写天然一致，OpenResty 读取最简单，**无密钥、无共享状态问题**。`TrafficTagSigner` 类保留不删（不执行，未来可复用），`TrafficTagResolver` 的签名分支在 `signingEnabled=false` 时不进入。

**固有特性（接受）**：首次无Cookie请求走老后端→老后端算tag写Cookie→下一跳才到新后端；未登录用户返回defaultTag；Cookie 保证会话粘性。

## 规则 JSON 格式（存 Redis key `geelato:gray:rules`）

```json
[
  {"targetType":"USER","targetValue":"zhangsan,lisi","priority":100},
  {"targetType":"ORG","targetValue":"org_001","priority":90},
  {"targetType":"TENANT","targetValue":"tenant_a","priority":80},
  {"targetType":"PERCENT","targetValue":"5","priority":50}
]
```
- 字段：`targetType`(USER/ORG/DEPT/BU/TENANT/PERCENT/ALL)、`targetValue`(多值逗号分隔；PERCENT 为0~100)、`priority`(可选，越大越先，默认0)、可选 `grayTag`(默认 "gray")
- 命中任一条 → 返回 gray；全不命中 → default。user=null → default。
- Redis 无此 key 或 JSON 非法 → 视为空规则，全部走 default（安全降级）。

## 实施步骤

### 步骤 1：关闭签名（改默认值）
**修改** `geelato-web-common/.../traffic/TrafficColoringProperties.java`
- `private boolean signingEnabled = true;` → `private boolean signingEnabled = false;`
- 一行改动。Cookie 写/读均走裸 tag 分支（现有代码已支持，无需改 Resolver/Signer）。

### 步骤 2：JsonGrayRuleProperties（配置类，默认值内置，不暴露到 properties）
**新建** `geelato-web-common/.../traffic/JsonGrayRuleProperties.java`
- `@Data @Component @ConfigurationProperties(prefix="geelato.traffic.gray")`
- 字段（均给默认值，用户无需配置）：
  - `boolean enabled = true`
  - `String redisKey = "geelato:gray:rules"`
  - `String hashSalt = "geelato"`

### 步骤 3：GrayRuleMatcher（规则匹配核心，纯内存，无DB）
**新建** `geelato-web-platform/.../srv/gray/GrayRuleMatcher.java`
- 注入 `StringRedisTemplate`、`JsonGrayRuleProperties`、`TrafficColoringProperties`
- `volatile List<GrayRule> rules`（内存缓存）
- `@PostConstruct load()`：从 Redis 读 key → fastjson2 解析 → 存内存；异常/空 → 空列表（记 warn 日志，不抛异常）
- `reload()`：重新 load（reload 接口调用）
- `String resolve(User user)`：
  - user==null → 返回 defaultTag
  - rules 按 priority 降序遍历，命中返回该规则 grayTag（或默认 grayTag），否则 defaultTag
  - PERCENT：`Math.floorMod((user.getUserId()+salt).hashCode(), 100) < percent` 命中
  - USER 比对 loginName/userId；ORG 比对 orgId；DEPT 比对 deptId；BU 比对 buId；TENANT 比对 tenantCode；ALL 直接命中

**内部轻量 POJO** `GrayRule`（非@Entity，仅 fastjson2 反序列化用）：targetType/targetValue/priority/grayTag

### 步骤 4：JsonRuleTrafficTagStrategy（接入现有染色链路，零改动）
**新建** `geelato-web-platform/.../srv/gray/JsonRuleTrafficTagStrategy.java`
- `implements TrafficTagStrategy`，`@Component @Primary`（覆盖 `WhitelistTrafficTagStrategy`，避免多 Bean 冲突）
- `resolveTag(request, user)` → `grayRuleMatcher.resolve(user)`
- `InterceptorConfiguration` 已 `@Autowired(required=false) TrafficTagStrategy`，`@Primary` 自动选中，**无需改拦截器**

### 步骤 5：reload REST 接口
**新建** `geelato-web-platform/.../srv/gray/GrayRuleController.java`
- `@ApiRestController("/gray-rules")`，`extends BaseController`
- `POST /reload` → 调 `grayRuleMatcher.reload()` → 返回新规则条数
- `GET /get` → 返回当前内存中的规则（便于运维核对）
- 走正常鉴权（管理接口需登录）

### 步骤 6：OpenResty 路由配置（新建，代码库目前没有）
**新建** `deploy/openresty/nginx.conf`
- 两个 upstream：`backend_old`(老,如8081)、`backend_new`(新,如8082)
- lua 读 cookie `gl_traffic_tag`（裸值，非签名格式）：值==gray → 新后端，否则老后端
- `set $upstream_name` + `proxy_pass http://$upstream_name/`（配 upstream 组）；透传 `X-Gl-Traffic-Tag` 头
- 后端 `Set-Cookie` 原样透传回浏览器

### 配置（零改动 application.properties）
**不改 application.properties**。所有配置走代码默认值：signingEnabled=false、gray.enabled=true、redis-key=geelato:gray:rules。
新老后端只需共用同一 Redis。

## 灰度操作流程
1. 运维 `redis-cli SET geelato:gray:rules '[{"targetType":"USER","targetValue":"zhangsan","priority":100}]'`
2. 调 `POST /api/gray-rules/reload` → 刷内存（返回规则条数确认）
3. zhangsan 登录 → 老后端算出 gray 写裸 Cookie → 刷新页面 OpenResty 读 cookie 路由到新后端
4. 放量：改 JSON 为 `PERCENT 5` → reload → 5% 用户灰度 → 观察 → 50 → 100
5. 回滚：`SET geelato:gray:rules '[]'` + reload → Cookie 过期/校准为 default → 全量回老后端

## 关键风险与规避
| 风险 | 规避 |
|---|---|
| 首跳落老后端 | SpringBoot 染色固有特性，方案已接受 |
| Cookie 伪造绕过灰度 | 灰度消费方是路由+功能开关，伪造顶多进新后端，无权限提升风险，可接受 |
| Cookie 域名/路径导致 OpenResty 读不到 | `cookieDomain`/`cookiePath` 覆盖到网关域名（默认 "/" 已可用） |
| 新后端故障导致灰度用户 5xx | OpenResty 加 `proxy_next_upstream` 或 lua 健康检查；紧急清规则回滚 |
| Redis JSON 非法 | load 时 try-catch → 空规则 → 全走 default（安全降级） |

## 改动范围
- **修改（1行）**：`TrafficColoringProperties.signingEnabled` 默认值 true → false
- **新增（后端，~5个Java文件）**：JsonGrayRuleProperties、GrayRuleMatcher(+内部 GrayRule POJO)、JsonRuleTrafficTagStrategy、GrayRuleController
- **新增（部署）**：`deploy/openresty/nginx.conf`
- **不改**：application.properties / TrafficTagResolver / TrafficTagSigner / TrafficTagContext / DefaultSecurityInterceptor / InterceptorConfiguration
- **不建表、不建实体、不签名、不暴露配置**：规则纯 JSON 存 Redis

## 两阶段交付
- **阶段一（染色+规则）**：步骤1-5，先验证后端正确写裸 tag、Cookie 分布正确（OpenResty 暂单 upstream）
- **阶段二（路由分流）**：步骤6，OpenResty 双 upstream 真正按 tag 分流
