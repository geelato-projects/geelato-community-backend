# 修复 /meta/list 链路上 @pf 视图模板参数静默丢失的问题

## 根因(已确认)

`/api/meta/list` 传 `@pf` 时,视图模板参数在链路上被"双重提取"后静默丢失:

1. `MetaRuntimeController.resolveQueryPayload()`(`geelato-web-platform/.../srv/meta/MetaRuntimeController.java:99-117`)调 `extractPfAndSerialize` 把 `@pf` 从请求 JSON **删除**,参数存入 `paramsByEntity`,把「净化后的 gql + paramsByEntity」传给 `ruleService.queryForMapList(gql, withMeta, paramsByEntity)`。
2. `RuleService.queryForMapList`(`geelato-web-platform/.../srv/platform/service/RuleService.java:105-107`)委托 `MqlQueryProcessor.getInstance().process(gql)` —— **只传了 gql,`queryParamsByEntity` 收而不用**。
3. `MqlQueryProcessor.process()`(`geelato-core/.../mql/MqlQueryProcessor.java:84-93`)的契约是"输入原始含 @pf 的 JSON,内部自己提取"。此时 @pf 已被删,二次提取得空 map;`applyViewTemplateParams`(行 124)遇空 map 直接 return,`command.viewTemplateParams` 恒为 null。
4. `MetaQuerySqlProvider.renderSegment`(`geelato-core/.../sql/provider/MetaQuerySqlProvider.java:530-531`)取不到 `salesmanId` → `isBlankValue` → 视图构造 SQL 中整个 `# ... {salesmanId} ... #` 段被消除 → **业务员过滤条件无声消失,返回未过滤全量数据**。

对照:`/meta/multiList` 正确(`RuleService.java:192` 显式调 `applyViewTemplateParams(command, queryParamsByEntity)`);Playground/测试场景直接传原始 JSON 给 `process()` 也正确。是 `queryForMapList` 重构为委托 `process()` 五步链路时遗留的职责不对称。

## 修复内容

### 改动 1:MqlQueryProcessor 增加外部参数注入重载(geelato-core)

`MqlQueryProcessor.java`:
- 现 `process(String mqlJson)` 改为委托 `process(mqlJson, null)`,对外行为不变。
- 新增 `process(String mqlJson, Map<String, Map<String, Object>> externalParamsByEntity)`:
  - 内部 `extractPfAndSerialize` 照常执行(兼容原始 JSON 直传场景);
  - `externalParamsByEntity` 非空时,按实体 merge 进本次提取的 `paramsByEntity`,**外部值优先**(同 key 覆盖 JSON 内提取值);
  - 后续 parse → applyViewTemplateParams → processQueryCommandFunctions → generatePageQuerySql 不变;
  - `ProcessedQuery.paramsByEntity` 返回合并后的结果。
- 同步更新类 javadoc 中五步链路说明。

### 改动 2:RuleService.queryForMapList 传透参数(geelato-web-platform)

`RuleService.java:107`:`process(gql)` → `process(gql, queryParamsByEntity)`。修复后缓存 key 自动正确(`signatureString()` 的 "pf" 段会包含 salesmanId,与历史脏缓存天然隔离)。

### 改动 3:applyViewTemplateParams 硬失败门(geelato-core)

`MqlQueryProcessor.applyViewTemplateParams`(行 123-144):当 `paramsByEntity` 含该实体的**非空参数**,但实体不满足生效条件时,不再静默 return,改为抛 `CoreException` 子类:
- 非 View 实体 → 消息含实体名、收到的参数名列表、"非视图实体,不支持 @pf 参数";
- COMPLEX 视图 → 消息含视图类型、参数名列表、"仅支持 DEFAULT 视图";
- 新建异常类(如 `ViewTemplateParamException extends CoreException`),ERROR_CODE 在 10xxx 数据段取未占用值(实施时核对,JsonParseException=10001 已占用),遵循"错误码内聚在异常类"的既有惯例。
- 不带 @pf 的查询路径零影响;`queryForMultiMapList` 走同一方法,同样受益。

### 改动 4:回归测试(geelato-mql-test)

在 `geelato-mql-test/src/test/java/cn/geelato/mqltest/sql/DialectAndViewSqlTest.java`(或同模块邻近测试类)新增:
- **复现测试**:先 `extractPfAndSerialize` 模拟 Controller 预提取 → `process(cleanGql, paramsByEntity)` → 断言 BoundPageSql 的 SQL 渲染出 salesman 过滤值;同时断言 `process(cleanGql)`(不传外部参数)保持段消除行为,证明修复点即原 bug。
- **硬失败测试**:非视图实体带 @pf 参数 → 断言抛异常且消息含实体名与参数名。

## 验证

1. `mvn clean compile -pl geelato-lang,geelato-core,geelato-web-platform -am`(先 clean,规避 ECJ 坏字节码残留)。
2. `mvn test -pl geelato-mql-test -Dtest=DialectAndViewSqlTest`(含新增用例)。

## 使用方提醒(非代码改动)

修复后若 `v_il_so_container_fee_aging_reporv` 的 @pf 仍不生效,需按序检查实体配置(这是设计语义,非代码 bug):entityType=View、viewType=DEFAULT(或空)、view_construct 中含 `# ... {salesmanId} ... #` 模板段(示例写法:`# {salesmanId} and salesman_id = {salesmanId} #`)。
