## 文件 1：`reference/metastore-extension.md`（80 → ~360 行）

### 新增前置：「为什么要抽象 MetaStore」（放在「可见扩展点」之前）
**讲清楚痛点与设计动机：**
- 早期元数据来源硬绑 `platform_dev_*` 五张设计器表：`DefaultMetaStore` 直接 SQL 查表 → 框架层（geelato-core）与"平台表结构"强耦合。
- 由此带来的三个具体痛点（用场景化语言，非抽象说教）：
  1. 新项目/轻量项目不想建一整套平台设计器表，就用不上元数据驱动（ORM、MQL、动态表单）。
  2. 元数据定义来自别的系统（配置中心、外部元数据服务、构建产出的 JSON）时，被迫改框架源码。
  3. 框架层本应是纯净抽象，却背着具体存储结构的依赖，难以独立复用。
- **设计决策**：把"元数据从哪来"抽象成 `MetaStore` SPI（放框架层）；"从平台表读"降级为**众多实现之一**（`DefaultMetaStore` 迁至业务层 `geelato-web-platform`，但保留原 package 以兼容 import）。
- **架构权衡**：选 Spring DI 风格 SPI 而非 JDK `ServiceLoader` —— 框架本就基于 Spring，DI 装配更自然，且支持 `@Primary`/`@ConditionalOnXxx` 等条件化注入，比 `META-INF/services` 更灵活。

### 新增：「对使用者有什么好处」（紧跟设计动机，用清单+一句话场景）
1. **零改框架**：实现接口 + `@Component @Primary`，整条来源链路被替换，不动框架一行代码。
2. **不必建平台表**：最小接入可用 JSON 文件或内存定义起步，后续按需升级到平台表。
3. **来源由你定**：文件 / 配置中心 / 外部 API / 任意存储，框架不关心。
4. **能力全继承**：换来源后，`MetaManager` 的扫描、缓存、冲突检测、实体→数据源路由、ORM/MQL/字段填充等下游能力**自动复用**，无需重写。
5. **可与默认实现并存**：支持灰度迁移，catalog=platform 的平台实体仍走 Java 类，业务实体走自定义来源。

### 保留并轻量调整现有概念章节
「可见扩展点 / 默认实现 / 装配方式 / 替换场景 / 实现边界 / 使用建议」保留，措辞与上述价值叙述衔接。

### 新增：⚠️ 覆盖机制 —— 必须加 `@Primary`（核心陷阱）
- `DefaultMetaStore` 是 `@Component` 且无 `@Primary`；注入点 `@Autowired(required=false)` 无 `@Qualifier`。
- 直接 `@Component implements MetaStore` → `NoUniqueBeanDefinitionException`（`required=false` 只允许零个，不容忍多个）。
- 推荐 `@Component @Primary`；勿靠 bean 名覆盖（`allow-bean-definition-overriding` 默认 `false`）。
- 这一小节呼应"零改框架"的好处：**正因为框架用了标准 Spring 装配，你才不必改源码**。

### 新增：契约与字段约定（支撑"怎么用"）
- 三方法签名 + `MetaDefinitionBundle` 构造器（五 List，null 安全）。
- 关键约束（源码核实）：`columnList` 不能空；`tableMap` 必须含 `entity_name`。
- tableMap / columnMap 字段速查表（必需 vs 可选，标注"驱动数据源路由""驱动 Java 类型""驱动主键"等用途，让字段与价值挂钩）。

### 新增：三个完整示例
- A · 内存构造（最小演示，快速验证契约）。
- B · JSON 文件（最常见实战，附 JSON 结构）。
- C · 外部 HTTP API（从元数据服务拉取）。
- 每例含完整 package+import+中文注释+预期结果，统一 `@Component @Primary`。

### 新增前置（在该段开头）：为什么要抽象数据源来源
**痛点与设计动机：**
- 早期动态数据源定义硬绑 `platform_dev_db_connect` 表 → 同样把框架层（geelato-orm）与具体表耦合。
- 痛点场景化：
  1. 多环境（开发/测试/生产）数据源配置散落在数据库，难统一管控，改库要登 SQL。
  2. 想用配置中心（Nacos/Apollo）集中管理、动态推送，得绕框架。
  3. 轻量项目为用多数据源，被迫引入一整套平台表。
- **设计决策**：抽象 `DynamicDataSourceDefinitionLoader` SPI（放 geelato-orm）；默认 `PlatformDynamicDataSourceDefinitionLoader` 迁至业务层；`DynamicDataSourceRegistry` 对 loader `@Nullable` 注入 —— **不提供 loader 时只走 primary/secondary，框架可独立运行**。

### 新增：对使用者的好处（清单+场景）
1. **配置中心统一管理**：Nacos/Apollo 管多环境，改配置即生效（配合热刷新）。
2. **零改框架**：接口 + `@Primary`。
3. **不必引入平台表**：文件/内存起步。
4. **运维友好**：换库、扩库不改代码不重启（host 映射 + 两步热刷新）。
5. **能力全继承**：懒加载、连接池调优、Seata/JTA、实体→数据源自动路由全复用。

### 新增：覆盖机制提醒（同 MetaStore 同构）
`PlatformDynamicDataSourceDefinitionLoader` 是 `@Component` 无 `@Primary`；注入点 `@Nullable` 无 `@Qualifier`；不加 `@Primary` 同样报 `NoUniqueBeanDefinitionException`。

### 新增：Map 字段约定表（支撑实现）
- `id`[路由key] / `db_type`[必需] / `db_hostname_ip`[必需] / `db_port`[必需] / `db_user_name`[必需] / `db_name`[必需] / `db_password`[可选]。
- `db_type`：`mysql` / `postgresql`(或 `postgres`)，其他抛 `UnsupportedOperationException`。
- 密码：明文 OK；加密须 `algorithm:ciphertext`（`aes`/`rsa`/`sm2`/`sm4`），无前缀按明文透传。

### 把骨架示例扩成三个完整示例
- A · 内存构造；B · JSON/YAML 文件（附加密密码写法）；C · 外部 HTTP API（从"数据库连接注册中心"拉取）。

### 新增：运行时热刷新（呼应"运维友好"好处）
- 两步缺一不可：`DynamicDataSourceRegistry.refreshXxx`（重建配置）+ `DynamicRoutingDataSource.refreshXxx`（刷新路由表）。
- 替代路径：`DynamicDataSourceRegistry.registerDataSource(key, ds)` 直接注册已构建 DataSource。

### 排障表增补两行
- `UnsupportedOperationException: 不支持的数据库类型` → `db_type` 非法。
- 改了来源但切源没生效 → 未同步刷新 Registry + RoutingDataSource。

## 叙事原则（两篇统一）

- **先 Why 后 How**：每个主题先讲痛点/动机/好处（使用者视角），再落到契约与代码。
