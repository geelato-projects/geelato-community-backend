# ORM 事件机制重构：触发模板收敛 + 修复执行路径行为漂移

## 背景与结论

ORM 事件体系的语义设计（before 同步/after 异步/事务感知回调）本身对标了 Hibernate/JPA/Spring 的业界标准，**问题在于触发样板在代码里手写了 23 遍**，且已造成两条执行路径的实际行为漂移：

- `Dao.java`（geelato-core）17 处触发点，每处手写同一套 6 步模板（构造 ctx → fireBefore → try/SQL → catch 回填+rethrow → 成功回填 → fireAfter → `EventTransactionSupport.trigger`）
- `JdbcTemplateMetaExecutionStrategy.java`（geelato-orm）6 处触发点，与 Dao 路径存在 **3 个已确认缺陷**：
  1. `save/delete` 不回填 `success/exception`（监听器看到的状态不完整）
  2. `save/delete/multiSave` 不调 `EventTransactionSupport.trigger`（事务感知监听器在该路径静默失效）
  3. `multiSave` 的 `fireBefore` 在 try 块外（before 监听器抛异常时事务悬挂；Dao.multiSave 已修过同样问题并留有 A3 注释，但没同步过来）

业界做法（Hibernate `SessionImpl.fire*` 模板收敛、Spring `TransactionTemplate.execute`）证明正确路线是：**触发顺序只在一处定义，所有执行路径委托**。纯 AOP 不适用（事件上下文需要方法内部构造的 BoundSql/command/valueMap/行数，切面拿不到）。

## 实施方案

### 1. 新建模板类 `cn.geelato.core.orm.event.OrmEventOperations`（geelato-core）

一个 final 工具类 + 3 个函数式接口，把事件编排顺序收敛为唯一事实来源：

```java
public final class OrmEventOperations {
    /** 单条保存：fireBefore(纳入try) → action → 成功/失败回填 → fireAfter → trigger */
    public static void save(SaveEventContext ctx, SaveAction action);
    /** 批量保存（一次 batchUpdate + N 个 ctx）：循环 fireBefore → action → 批量回填 → 逐个 fireAfter+trigger */
    public static void batchSave(List<SaveEventContext> contexts, BatchSaveAction action);
    /** 单条删除 / 批量删除：对称 */
    public static void delete(DeleteEventContext ctx, DeleteAction action);
    public static void batchDelete(List<DeleteEventContext> contexts, BatchDeleteAction action);
    /** 查询：fireBefore → action → 回填 rowCount/success/exception → fireAfter（无 trigger） */
    public static <T> T query(QueryEventContext ctx, QueryAction<T> action);
}
```

关键语义细节（从现有代码逐条对齐，不改行为）：
- `save/delete`：`fireBefore` 纳入 try（A3 语义），catch 中 `setSuccess(false)/setException(ex)` 后 rethrow；成功路径 `setSuccess(true)` + `setResultValueMap`/`setAffectedRows` 回填，然后 `fireAfter` + `EventTransactionSupport.trigger`
- `query`：action 返回结果集，模板回填 `rowCount/success/exception`，无事务回调
- 事务的 begin/commit/rollback **仍留在 Dao/Strategy**（模板只管事件编排，不管事务边界）

### 2. 改造 `Dao.java` 的 17 处触发点

- `save(BoundSql)` L279-298、`doSave(E, CommandType)` L581-600、`delete(BoundSql)` L380-394、`delete(Class,field,value)` L791-805 → 各变为一行 `OrmEventOperations.save(context, () -> updateWithTypes(bs))`
- `batchSave` L303-334 → `OrmEventOperations.batchSave(contexts, () -> jdbcTemplate.batchUpdate(...))`
- `multiSave` L336-368、`multiDelete` L415-432 → 循环体调单条模板，外层 Dao 保留事务 begin/rollback/returnPks.clear 逻辑（模板 catch-rethrow 后由 Dao 处理回滚）
- 查询 3 处（`queryForMapListWithFilter` L151-163、`queryList` L613-626 等）：现有 `fireQueryBefore/fireQueryAfter` helper 改为内部委托 `OrmEventOperations.query`

### 3. 改造 `JdbcTemplateMetaExecutionStrategy.java` 的 6 处触发点

全部替换为模板调用，**自动修复 3 个缺陷**（success 回填、trigger 缺失、multiSave 事务悬挂），其 `jdbcSupport.executeUpdate` 作为 action 传入。

### 4. 测试与验证

- 已有测试必须全绿：`geelato-core/src/test/.../OrmEventMechanismTest.java`、`EventTransactionSupportTest.java`
- 新增模板单测（geelato-core）：before 异常回填+透传、fireAfter 在成功后才触发、trigger 顺序、query 失败回填、batchSave 失败批量回填
- 运行 `mvn -pl geelato-core,geelato-orm -am test`
- 检查 `docs/orm/` 下相关文档是否需要同步

## 明确不做（保持语义 100% 不变）

- 不扩大事件覆盖范围（`executeUpdate`/`pageQueryList` 等原来不发事件，改完也不发——属行为变更，留待单独决策）
- 不动三个静态 EventManager 的注册 API 与监听器接口（AuditLog/EsSync/QueryCacheEvict 三个使用方零改动）
- 不做 `@OrmEventListener` 声明式注册、不做静态 Manager Bean 化（后续可选项）
