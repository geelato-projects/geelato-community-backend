# 安全主体业务扩展机制（Security Principal Extension）实施计划

## 目标

security 模块保持纯契约、零依赖不变，且**自包含整个扩展机制**（载体、SPI、发现与执行）：平台层/业务模块通过注册「安全主体增强器」把业务特性信息加载进 `User`/`UserOrg`/`Tenant`；开发者仍通过 `SecurityContext.getCurrentUser().getAttribute(...)` / `getExtension(...)` 直接获取扩展信息。

## 设计总览

```
geelato-security（机制全部在此，纯 JDK 零依赖）
  ├─ ① 扩展载体：Extensible 基类（动态属性 + 类型化扩展对象）
  ├─ ② 扩展点 SPI：SecurityPrincipalEnhancer
  └─ ③ 发现与执行：SecurityPrincipalEnhancerRegistry（静态注册表 + bean 供给器 + 排序 + 异常隔离执行）
geelato-core（仅两处薄接线）
  ├─ Spring 桥：BeansUtils.getBeansOfType → 注入 registry 的 beanSupplier
  └─ 挂载点：EnvManager.InitCurrentUser 调用 registry.enhance(user)
geelato-web-platform
  └─ ④ 平台默认实现：ext_attributes JSON 列加载增强器
```

**关键决策**：
- **API 风格**：动态属性 Map（`getAttribute("costCenter")`，利于规则/模板取值）+ 类型化扩展对象（`getExtension(HrUserExt.class)`，编译期安全），两者并存，由同一 SPI 填充。
- **多实例叠加语义**：与 `UserOrgInfoEnricher` 的 `@ConditionalOnMissingBean` 单覆盖不同，增强器允许多个共存、按 `getOrder()` 升序叠加（多个业务域各加各的属性）。
- **零依赖约束下的发现机制**：security 模块无 Spring，注册表提供两条注册通道——程序化 `register(...)`（任何模块、非 Spring 场景、测试）+ `setBeanSupplier(...)`（由 core 的 Spring 桥注入，自动发现所有 bean）。执行时机在 `EnvManager.InitCurrentUser` 加载用户后、入缓存前（非每请求执行）；扩展属性与基础信息同生命周期：30 分钟缓存 + `clearUserCache` 失效，`tokenContextCache` 自动携带（属性在对象上）。
- **SystemToken 虚拟用户**（`new User()` 直接构造、不走 `InitCurrentUser`）不被增强，增强器实现中可自行防御 `systemPrincipal`。

## 第一步：扩展载体（geelato-security）

### 1.1 新增 `geelato-security/src/main/java/cn/geelato/security/Extensible.java`

```java
/**
 * 可扩展安全主体基类：承载业务扩展属性（动态标量）与类型化扩展对象。
 * 实例可能被 EnvManager/tokenContextCache 缓存并跨线程共享，内部使用并发容器。
 */
public abstract class Extensible {
    private final Map<String, Object> attributes = new ConcurrentHashMap<>();
    private final Map<Class<?>, Object> extensions = new ConcurrentHashMap<>();

    public Object getAttribute(String key);
    public <T> T getAttribute(String key, Class<T> type);   // 带类型转换，null 安全
    public void setAttribute(String key, Object value);
    public boolean hasAttribute(String key);
    public <T> T getExtension(Class<T> type);               // 无则 null
    public void setExtension(Object extension);             // 按 extension.getClass() 存
    public Map<String, Object> getAttributes();             // 只读视图
}
```

### 1.2 三个类各改一行继承

- `UserCore extends Extensible`（`User` 随之获得能力）
- `OrgCore extends Extensible`（`UserOrg`、`Org` 随之获得能力）
- `Tenant extends Extensible`（已有 `configuration`/`properties` 两个 map 占位保留不动以兼容，`attributes` 成为标准扩展入口）

`PlatformEnvStore` 的 `BeanPropertyRowMapper<>(User.class)` 不受影响（无同名列）。模块内已有 slf4j 使用先例（`PermissionRuleUtils` 用 `@Slf4j`），日志可用。

## 第二步：扩展点 SPI（geelato-security）

### 新增 `geelato-security/src/main/java/cn/geelato/security/SecurityPrincipalEnhancer.java`

```java
/**
 * 安全主体增强器：在用户上下文组装完成后为其填充业务扩展信息。
 * 可多个实现共存，按 getOrder 升序全部执行。
 * enhance 中可访问 user.getUserOrgs()/user.getTenant() 一并填充组织、租户的扩展属性。
 * 实现方需自行防御 systemPrincipal 用户与 null userOrgs。
 */
public interface SecurityPrincipalEnhancer {
    void enhance(User user);
    default int getOrder() { return 0; }
}
```

## 第三步：发现与执行（geelato-security，纯 JDK）

### 3.1 新增 `geelato-security/src/main/java/cn/geelato/security/SecurityPrincipalEnhancerRegistry.java`

静态工具类（`@Slf4j`，参照模块内 `PermissionRuleUtils` 风格）：

```java
public final class SecurityPrincipalEnhancerRegistry {
    private static final CopyOnWriteArrayList<SecurityPrincipalEnhancer> manualEnhancers = ...;
    private static volatile Supplier<Collection<SecurityPrincipalEnhancer>> beanSupplier; // Spring 侧注入

    public static void register(SecurityPrincipalEnhancer enhancer);      // 程序化注册
    public static void unregister(SecurityPrincipalEnhancer enhancer);
    public static void setBeanSupplier(Supplier<Collection<SecurityPrincipalEnhancer>> s);
    public static List<SecurityPrincipalEnhancer> getEnhancers();         // manual + supplier 合并，按 getOrder 排序
    public static void enhance(User user);   // 逐个执行；单个抛异常仅 log.warn（含类名），不中断
    public static void clear();              // 测试用
}
```

- `enhance` 每次调用时通过 supplier 惰性取 bean（`BeansUtils` 在 context 未就绪时返回空集，安全降级；用户 30 分钟缓存下调用频率极低，无性能问题）。
- 空注册表时 `enhance` 直接返回，零开销。

### 3.2 修改 `geelato-core/.../env/EnvManager.java`（仅两行接线）

1. 构造/静态初始化中注入 Spring 桥：
   `SecurityPrincipalEnhancerRegistry.setBeanSupplier(() -> BeansUtils.getBeansOfType(SecurityPrincipalEnhancer.class).values());`
2. `InitCurrentUser` 中，`loadUserOrg/loadTenant/loadUserRole` 之后、`userCache.put` 之前插入：
   `SecurityPrincipalEnhancerRegistry.enhance(user);`

缓存命中路径不重复执行。委托代办 `applyDelegation`、OAuth2、微信扩展键等所有走 `InitCurrentUser` 的认证路径自动获得增强。

## 第四步：平台默认实现（geelato-web-platform）

### 4.1 DDL

- `geelato-app-scaffold-starter/init/platform_user.sql`：`platform_user` 增加 `ext_attributes json NULL COMMENT '业务扩展属性'`
- `geelato-app-scaffold-starter/init/platform_org.sql`：`platform_org` 同样增加 `ext_attributes json NULL`
- 文档中给出升级语句：`ALTER TABLE platform_user ADD COLUMN ext_attributes json NULL;`（org 同理）

### 4.2 新增 `geelato-web-platform/src/main/java/cn/geelato/security/PlatformPrincipalEnhancer.java`

与 `JdbcUserSnapshotLoader` 同包。`@Component`（由包扫描自动成为 bean，经 Spring 桥被发现），实现 `SecurityPrincipalEnhancer`：

- 用 `JdbcTemplate` 按 `user.getUserId()` 查 `platform_user.ext_attributes`，按 `userOrgs` 的 orgId 批量查 `platform_org.ext_attributes`；
- Jackson 解析 JSON → 逐键 `setAttribute(...)`；
- **容错**：JSON 为 null/空 → no-op；SQL 报列不存在（旧库未升级）→ `log.warn` 一次并自禁用（volatile 标志），零成本降级。

## 第五步：数据权限规则联动（geelato-security）

修改 `PermissionRuleUtils.getFieldValueWithMapping`：在现有白名单 `default ->` 抛异常之前，回退两级：

1. `user.getAttributes().get(fieldName)`（支持任意业务属性键，含带点号的键）
2. `defaultOrg.<key>` 路径：解析前缀后查 `user.getDefaultOrg().getAttributes()`

效果：业务扩展属性可直接写进数据权限规则，如 `#currentUser.costCenter#`。更新类 javadoc 中的允许字段说明。

## 不做的事（边界）

- 不改 `DefaultSecurityInterceptor`（挂载点在 `EnvManager`，所有认证路径自动覆盖）；
- 不动 Shiro `ShiroUser`、`cn.geelato.meta.User/Org`（持久化实体，另一套体系）；
- 不引入 Java ServiceLoader / Spring 依赖进 security 模块 / 新第三方依赖；
- `Tenant.configuration/properties` 旧占位 map 保留不迁移，仅让 Tenant 继承 `Extensible` 统一入口。
