# 平台站内信（通知中心）测试文档

> 适用范围：`geelato-community` 的 `srv/notification` 子系统。
> 前置条件：已部署 community 后端 + geelato-front 前端；已登录（持有有效 `Authorization` 头）。

---

## 一、测试环境与准备

### 1.1 接口前缀
所有接口走 `/api` 前缀（`@ApiRestController("/notification")` → 实际路径 `/api/notification/...`）。

### 1.2 鉴权
所有接口需在请求头携带登录令牌：
```
Authorization: Bearer <你的token>
Accept-Language: zh-CN
Content-Type: application/json
```
> `/api/notification/pageQuery`、`/unread-count`、`/read/*`、`/star/*`、`/archive/*` 强制按**当前登录用户**过滤，防越权。
> `/api/notification/send`、`/recall` 需要登录态但接收方由请求体指定。

### 1.3 准备测试账号
| 角色 | userId | 说明 |
|---|---|---|
| 发送方 | `3751618121485025315` | 平台管理员（陈光兴，开发库默认账号） |
| 收件方A | `<userIdA>` | 登录后从「个人信息」或 `GET /api/user/info` 获取 |
| 收件方B | `<userIdB>` | 第二个账号，用于验证"多人独立已读" |

> 获取当前登录用户 userId：登录前端后，浏览器 Console 执行 `JSON.parse(localStorage.getItem('user'))?.id`，或调用 `GET /api/user/info` 看返回 `id` 字段。

## 二、测试用例

### 用例 1：发送单条站内信（核心闭环）

**目标**：验证 `/send` 写入主体 + outbox，调度器 fan-out 到收件人 inbox，前端实时收到。

**请求**：
```http
POST /api/notification/send
Authorization: Bearer <token>
Content-Type: application/json

{
  "recipients": ["<userIdA>"],
  "title": "合同 HT-001 待审批",
  "content": "合同 HT-001 已提交，请尽快审批。",
  "bizType": "contract",
  "bizId": "HT-001",
  "actionUrl": "/contract/approve?id=HT-001",
  "senderType": "user"
}
```

**预期响应**：
```json
{
  "code": 20000,
  "msg": "成功",
  "data": "<notificationId>"
}
```

**验证**（三个层面，发送后等 3 秒）：
1. **数据库**：
   ```sql
   -- 主体
   SELECT id, title, biz_type, biz_id, channels, sender_type, del_status
     FROM platform_notification WHERE biz_id = 'HT-001';
   -- 收件人状态（应为 1 行，read_status=0 未读）
   SELECT user_id, read_status FROM platform_notification_user WHERE notification_id = '<上面查到的id>';
   -- outbox（inapp 渠道应为 success）
   SELECT status, channel, retry_count FROM platform_notification_outbox WHERE notification_id = '<id>';
   ```
2. **接口**：用收件方A 的 token 调 `GET /api/notification/unread-count`，应返回 `data: 1`。
3. **前端**：收件方A 浏览器（已登录、未刷新）应在几秒内看到右上角铃铛红点 +1，下拉列表出现该通知。

---

### 用例 2：实时推送（不刷新页面）

**目标**：验证 SSE 推送链路完整。

**步骤**：
1. 收件方A 正常登录前端，保持页面打开（不要刷新）。
2. 发送方调用用例 1 的 `/send`（recipients 改为 A 的 userId）。
3. 观察 A 的浏览器。

**预期**：3 秒内（outbox 调度间隔），A 的铃铛角标自动 +1，**无需刷新页面**。
**排查**：若未实时收到，打开浏览器 Console，应有日志 `收到站内信推送 {...}`；网络面板应有一条持久的 `/subscribe/notice_user_<userIdA>` 连接（fetch 流）。

---

### 用例 3：多人独立已读（normalized 核心语义）

**目标**：验证一封通知发给多人，每人已读状态独立。

**请求**（发给 A 和 B 两人）：
```http
POST /api/notification/send

{
  "recipients": ["<userIdA>", "<userIdB>"],
  "title": "系统维护通知",
  "content": "系统将于本周六 02:00-04:00 维护。",
  "senderType": "system",
  "senderName": "系统"
}
```

**操作**：用 A 的 token 标记已读：
```http
POST /api/notification/read/<notificationUserId>
```
> `<notificationUserId>` 是 `platform_notification_user` 表的 `id`（不是 notification.id）。从 A 的 `POST /api/notification/pageQuery` 返回里取。

**验证**：
```sql
SELECT user_id, read_status, read_at FROM platform_notification_user
 WHERE notification_id = '<id>';
```
预期：A 的 `read_status=1`，B 的 `read_status=0`（互不影响）。

---

### 用例 4：收件箱分页查询

**请求**（用收件方A 的 token）：
```http
POST /api/notification/pageQuery

{
  "pageNum": 1,
  "pageSize": 10,
  "orderBy": "create_at DESC",
  "readStatus": 0
}
```

**预期**：返回当前用户（A）的未读通知，`data.items` 含通知字段（title/content/senderName/bizType/actionUrl/createAt/readStatus 等），`data.total` 为未读总数。
**越权校验**：即使伪造请求体传 `userId=<B>`，后端会强制覆盖为当前登录用户（A），不会返回 B 的收件箱。

---

### 用例 5：未读数（铃铛角标）

**请求**：
```http
GET /api/notification/unread-count
```
**预期**：`{ "code": 20000, "data": <未读数> }`。
**性能要点**：走 `SELECT COUNT(*) ... WHERE user_id=? AND read_status=0`（idx_user_unread 索引），不拉全量数据。

---

### 用例 6：全部已读

**请求**：
```http
POST /api/notification/read-all
```
**预期**：返回 `{ "data": <被标记条数> }`。
**验证**：
```sql
SELECT COUNT(*) FROM platform_notification_user
 WHERE user_id='<A>' AND read_status=0;  -- 应为 0
```
再调 `/unread-count` 应返回 0。

---

### 用例 7：点击跳转业务地址

**目标**：验证通知携带 `actionUrl`，点击后跳转业务页。

**步骤**：
1. 发送一条带 `actionUrl: "/contract/approve?id=HT-001"` 的通知（用例 1）。
2. 收件方A 在前端铃铛下拉或「消息中心」页面点击该通知。

**预期**：自动跳转到 `/contract/approve?id=HT-001`（内部路由 `router.push`）；若是 `https://...` 外部链接则新窗口打开。
> 该路由需存在，否则会跳到 404——这是正常的（验证跳转动作本身即可）。

---

### 用例 8：业务幂等（重复发送同一业务不重复创建）

**请求**：连续两次调用用例 1（`bizType=contract, bizId=HT-001` 完全相同）。

**验证**：
```sql
SELECT COUNT(*) FROM platform_notification WHERE tenant_code='<租户>' AND biz_type='contract' AND biz_id='HT-001';
```
**预期**：始终为 **1**（第二次发送复用已存在的主体，仅 outbox 层面幂等跳过）。

---

### 用例 9：撤回通知

**请求**：
```http
POST /api/notification/recall/<notificationId>
```
**预期**：`{ "data": true }`。
**验证**：
```sql
SELECT del_status FROM platform_notification WHERE id='<notificationId>';  -- 应为 1
```
撤回后，所有收件人的收件箱不再展示该通知（主体逻辑删除，关联失效）。

---

### 用例 10：归属校验（防越权）

**目标**：验证不能标记/归档他人的通知。

**步骤**：用 A 的 token，传入 B 的 `notificationUserId` 调用：
```http
POST /api/notification/read/<B的notificationUserId>
```
**预期**：返回 `{ "data": false }`（标记失败，因 `userId` 不匹配），B 的该通知仍为未读。

## 三、直接可用的测试数据（SQL + 接口）

### 3.1 快速造数：直接插入一条已送达的通知
> 跳过 outbox 调度，直接构造"已落库"的站内信，用于前端联调。

```sql
-- 1. 通知主体
INSERT INTO platform_notification
  (id, title, content, sender_id, sender_name, sender_type,
   biz_type, biz_id, action_url, channels, priority,
   tenant_code, del_status, update_at, updater, create_at, creator, delete_at)
VALUES
  ('TEST-NOTIF-001', '合同 HT-001 待审批', '合同已提交，请尽快审批。', 'system', '系统', 'system',
   'contract', 'HT-001', '/contract/approve?id=HT-001', '["inapp"]', 0,
   'geelato', 0, NOW(), 'system', NOW(), 'system', NULL);

-- 2. 收件人状态（把 <userIdA> 换成你的实际 userId）
INSERT INTO platform_notification_user
  (id, notification_id, user_id, read_status, read_at, starred, archived,
   tenant_code, del_status, update_at, updater, create_at, creator, delete_at)
VALUES
  ('TEST-NU-001', 'TEST-NOTIF-001', '<userIdA>', 0, NULL, 0, 0,
   'geelato', 0, NOW(), 'system', NOW(), 'system', NULL);
```

造数后，用 A 的 token 调 `GET /api/notification/unread-count` → 应返回 1；`POST /pageQuery` → 列表含该条。

### 3.2 批量造数（测试分页/全部已读）
```sql
-- 把 <userIdA> 替换为实际值；造 15 条未读 + 5 条已读
INSERT INTO platform_notification
  (id, title, content, sender_type, channels, tenant_code, del_status, update_at, updater, create_at, creator, delete_at)
SELECT
  CONCAT('TEST-NOTIF-BULK-', LPAD(a.n + b.n*10, 3, '0')),
  CONCAT('批量测试通知 #', a.n + b.n*10),
  CONCAT('这是第 ', a.n + b.n*10, ' 条测试通知内容。'),
  'system', '["inapp"]', 'geelato', 0, NOW(), 'system', NOW(), 'system', NULL
FROM (SELECT 0 n UNION SELECT 1 UNION SELECT 2 UNION SELECT 3 UNION SELECT 4
      UNION SELECT 5 UNION SELECT 6 UNION SELECT 7 UNION SELECT 8 UNION SELECT 9) a
CROSS JOIN (SELECT 0 n UNION SELECT 1) b
WHERE a.n + b.n*10 < 20;

-- 收件人状态：前 15 条未读，后 5 条已读
INSERT INTO platform_notification_user
  (id, notification_id, user_id, read_status, read_at, starred, archived,
   tenant_code, del_status, update_at, updater, create_at, creator, delete_at)
SELECT
  CONCAT('TEST-NU-BULK-', LPAD(a.n + b.n*10, 3, '0')),
  CONCAT('TEST-NOTIF-BULK-', LPAD(a.n + b.n*10, 3, '0')),
  '<userIdA>',
  CASE WHEN a.n + b.n*10 < 15 THEN 0 ELSE 1 END,
  CASE WHEN a.n + b.n*10 < 15 THEN NULL ELSE NOW() END,
  0, 0, 'geelato', 0, NOW(), 'system', NOW(), 'system', NULL
FROM (SELECT 0 n UNION SELECT 1 UNION SELECT 2 UNION SELECT 3 UNION SELECT 4
      UNION SELECT 5 UNION SELECT 6 UNION SELECT 7 UNION SELECT 8 UNION SELECT 9) a
CROSS JOIN (SELECT 0 n UNION SELECT 1) b
WHERE a.n + b.n*10 < 20;
```

造数后验证：
- `GET /unread-count` → 15
- `POST /pageQuery` `{pageNum:1, pageSize:10, readStatus:0}` → total=15，items 10 条
- `POST /read-all` → 返回 15，再查 `/unread-count` → 0

### 3.3 清理测试数据
```sql
DELETE FROM platform_notification_user WHERE id LIKE 'TEST-NU-%';
DELETE FROM platform_notification WHERE id LIKE 'TEST-NOTIF-%';
DELETE FROM platform_notification_outbox WHERE notification_id LIKE 'TEST-NOTIF-%';
```

## 四、实时推送专项测试（SSE）

### 4.1 验证连接只建一条
收件方A 登录前端后，浏览器 DevTools → Network → 筛选 `subscribe`：
- 应有**且仅有一条** `/subscribe/notice_user_<userIdA>` 持久连接（Type 为 fetch，状态 pending）。
- 切换路由、刷新页面（重新登录态）后，**不应出现多条并发**的该连接。

### 4.2 验证不刷新实时收到
1. A 登录保持页面。
2. 发送方 `/send`。
3. A 不刷新，几秒内铃铛 +1。

### 4.3 验证断线重连（退避）
1. A 登录后，在 Network 面板对 `/subscribe/notice_user_...` 连接选 "Block request domain"（或断网）。
2. Console 应出现 `SSE 准备重连 {attempt:1, delayMs:1000}` → `attempt:2, delayMs:2000}` → 递增到上限停止。
3. 解除屏蔽/恢复网络，刷新页面后恢复正常。

## 五、geelato-message 外部渠道（可选，需配置）

> 仅当配置了 `geelato.notification.geelato-message.base-url` 时启用。不配置则跳过本节。

**请求**（站内信 + 邮件双渠道）：
```http
POST /api/notification/send

{
  "recipients": ["<userIdA>"],
  "channels": ["inapp", "email"],
  "title": "订单已发货",
  "content": "您的订单 SO-001 已发货。",
  "bizType": "order",
  "bizId": "SO-001",
  "senderType": "system"
}
```

**验证**：
```sql
SELECT channel, status FROM platform_notification_outbox WHERE notification_id='<id>';
```
预期：2 行——`inapp`(success) 和 `email`(由 GeelatoMessageChannel 调 geelato-message，成功则 success，失败则重试/死信)。

## 七、常见问题排查

| 现象 | 排查 |
|---|---|
| 发送后 outbox 长期 ready | 看后端日志 `notification-outbox-scheduler` 线程是否在跑；`SELECT status,next_retry_at,error_msg FROM platform_notification_outbox` 看是否在重试 |
| 未读数对不上 | 确认 `platform_notification_user` 是否有多余行（uk_notif_user 幂等保证不重复） |
| 前端不实时 | Network 看是否有 `/subscribe/notice_user_...` 连接；Console 看是否有 `收到站内信推送` 日志；确认 SSE 长连接未断 |
| 频繁请求 /subscribe/topic/all | 已修复（去重 + 退避），若仍出现检查是否启用了旧版 SseClient |
| pageQuery 报错 | 确认请求体是 POST + JSON，含 `pageNum`/`pageSize`；越权传 userId 会被强制覆盖为当前用户 |
