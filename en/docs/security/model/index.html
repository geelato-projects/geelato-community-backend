Security Model

This page documents the security model defined by geelato-security, attribute by attribute: six core entities, four attachment relation classes, and the relation rules between them. All classes live in the cn.geelato.security package as pure data contracts (POJOs) with no source or storage details; the platform DB column mapping is covered in Platform Defaults.

Model Map​

ModelResponsibility
TenantTenant, the multi-tenancy isolation dimension
AppApplication (subsystem), the fourth context dimension
OrgOrganization node (company / department / section, etc.), tree structure
UserUser (login principal), carries attachments and permissions
RoleRole, the carrier of permissions
PermissionPermission rule (data permission / element permission)
UserOrgUser-organization attachment (membership)
UserRoleDirectly attached role
UserOrgRoleUser-org role (department role, with source org)
OrgRoleOrg-attached role (role attached to a department)

Tenant and App​

Tenant​

AttributeTypeMeaning
codeStringTenant code, the unique identifier for tenant isolation
nameStringTenant name
configurationMap<String, Object>Tenant-level configuration (reserved; an empty HashMap today)
propertiesMap<String, Object>Tenant-level extended properties (reserved; an empty HashMap today)

Constructors Tenant(String code) and Tenant(String code, String name); both Maps are initialized empty at construction.

App​

AttributeTypeMeaning
idStringApplication identifier
nameStringApplication name
versionStringApplication version

App is the fourth SecurityContext thread dimension for subsystem identification; see Security Context.

Organization: OrgCore and Org​

The org model has two layers: OrgCore carries the tree structure and tenant ownership; Org adds company ownership and node type.

OrgCore​

AttributeTypeMeaning
orgIdStringOrg node ID; organizations are always referenced by it
codeStringOrg code, the stable business identifier
pidStringParent node ID; the org tree is built on it, empty at the root
nameStringOrg name
tenantCodeStringOwning tenant code

Org (extends OrgCore)​

AttributeTypeMeaning
(inherited)—orgId/code/pid/name/tenantCode, see above
companyIdStringOwning company ID (derived from the tree, filled during loading by relation resolution)
typeStringOrg node type, see table below; the key field for company resolution
extendIdStringCompany extension ID, carried on the company node, derived with company ownership

Platform values of type (OrgTypeEnum):

ValueMeaning
rootRoot org
companyCompany
departmentDepartment
sectionSection
factoryFactory
officeOffice

User: UserCore and User​

UserCore​

AttributeTypeMeaning
userIdStringUnique user ID (platform DB platform_user.id); users are always referenced by it
userNameStringUser display name
loginNameStringLogin name, one of the extended identity keys
tenantCodeStringOwning tenant code, the isolation dimension

User (extends UserCore)​

User is the core of the security model; its attributes are grouped by purpose below.

Identity and profile:

AttributeTypeMeaning
(inherited)—userId/userName/loginName/tenantCode, see UserCore
jobNumberStringJob number
descriptionStringDescription
enNameStringEnglish name
sexintGender; 0 female, 1 male (UserSexEnum)
avatarStringAvatar
mobilePrefixStringMobile country dialing prefix
mobilePhoneStringMobile number
telephoneStringLandline number
emailStringEmail
postStringPosition
nationCodeStringCountry/region code
provinceCodeStringProvince code
cityCodeStringCity code
addressStringDetailed address

Org ownership and derivations (filled during loading by UserOrgInfoEnricher, see Loading Abstractions):

AttributeTypeMeaning
orgIdStringThe department or section the user is directly attached to; resolved from attachments when empty (default org first)
orgNameStringName of the org referenced by orgId
defaultOrgIdStringDefault department ID
defaultOrgNameStringDefault department name
cooperatingOrgIdStringCooperating partner org ID
deptIdStringWhen the user is attached to a section, the ID of that section's parent department
buIdStringBusiness unit ID, filled from company ownership (same value as companyId)
buNameStringBusiness unit name
companyIdStringOwning company ID (the company node resolved from the tree)
companyNameStringCompany name
extendIdStringCompany extension ID, taken from the company node's extendId

Status:

AttributeTypeMeaning

Platform values of type (UserTypeEnum):

Extended identity keys:

AttributeTypeMeaning
weixinUnionIdStringWeChat UnionID, an extended identity key
weixinWorkUserIdStringWeCom (WeChat Work) user ID, an extended identity key

loginName, weixinUnionId, and weixinWorkUserId form the three extended identity entrances for extended-key authentication (see Authentication & Authorization); UserProvider.getUserByExtendKey looks users up by key type.

Delegation (acting on behalf):

AttributeTypeMeaning
delegateUserIdStringThe delegate (actual executor) ID; empty means the user acted personally
delegateUserNameStringThe delegate's name

Semantics: when an operation is executed by a delegate, creator/updater still record the effective identity (the delegating user); delegateUserId/delegateUserName exist only for audit — "who acted for whom". The same semantics apply when an engine (system principal) writes on a user's behalf: effective identity = owning user, delegate fields = engine system identity.

Generic extension:

AttributeTypeMeaning
extendInfoMap<String, Object>Generic extension attributes, filled by the upper layer via UserExtInfoEnricher at snapshot loading; concrete features (e.g. git binding) store values under agreed keys — the User layer never knows key meanings; values should be immutable objects (mostly strings)

:::note Two similar names extendId is the company extension ID (a String, taken from the company node); extendInfo is the generic extension map. They are different concepts. :::

Principal flag:

AttributeTypeMeaning
systemPrincipalbooleanWhether this is a system background principal (scheduled jobs and other contexts without HTTP). When true, data-permission filtering skips the default creator='<userId>' condition so the job can query all data of the current tenant; tenant isolation (tenantCode filtering) still applies

Relations and permissions:

AttributeTypeMeaning
userOrgsList<UserOrg>Org attachments (membership); multiple attachments returned together
userRolesList<UserRole>Directly attached roles
userOrgRolesList<UserOrgRole>Org-attached roles (with source org)
defaultOrgUserOrgDefault org object (the attachment with defaultOrg=true)
tenantTenantOwning tenant object
dataPermissionsList<Permission>Data permission rules
elementPermissionsList<Permission>Element permissions

:::note Default loading of permission collections The default platform snapshot does not fill the permission collections — permission-domain data belongs to the auth center, queried on demand via SecurityProvider.queryPermissionsOfUser (see Provider Contracts). Full-snapshot permission loading belongs to the auth-center implementation (AuthCenterSecurityProvider). :::

User behavior methods​

MethodSemantics
getEffectiveRoles()Effective roles = direct roles (userRoles) ∪ org-attached roles (userOrgRoles), deduplicated by role code. The unified entry for effective-role semantics; historical consumers (e.g. SecurityContext.isAdmin) keep reading direct roles only, unchanged
getDataPermissionByEntity(String entity)Per-entity data permission: filters dataPermissions by matching entity and takes the rule with the largest weight (first one on ties); returns null when the collection is missing or nothing matches
setupOrgInfo(OrgProvider orgProvider)Legacy compatibility entry: fills orgName/companyId/companyName/extendId/buId/buName/deptId (when empty)/defaultOrgName via OrgProvider. New code should prefer UserOrgInfoEnricher

Role​

AttributeTypeMeaning
IdStringRole ID. Note the field name starts with a capital letter; the getters/setters are getId/setId
codeStringRole code; business code and data-permission rules always reference roles by code (stable across environments), never by ID
nameStringRole name
typeStringRole type, see table below
tenantCodeStringOwning tenant code

Platform values of type (RoleTypeEnum):

ValueMeaning
platformPlatform-level role
appApplication-level role

Permission​

AttributeTypeMeaning
codeStringPermission code, the reference identifier (hasPermission matches on code)
entityStringEntity the permission belongs to; data permissions take effect per entity
nameStringPermission name
ruleStringPermission rule expression. For data permissions it is a filter condition that may contain #currentUser.xxx# variables; for element permissions it is the element identifier
weightIntegerData-permission weight; among multiple rules on one entity the largest weight wins
roleWeightIntegerWeight of the source role (carried when the permission is inherited through a role)

User variables in rules​

PermissionRuleUtils.replaceRuleVariable(Permission, User) replaces user variables in rule with the current user's field values before querying. Syntax: #currentUser.field#, with #currentUser.defaultOrg.field# supported to reach fields of the default org object.

Allowed field whitelist (strict camelCase; anything outside it throws IllegalArgumentException):

CategoryAllowed fields
Basic user fieldsuserId, orgId, defaultOrgId, cooperatingOrgId, companyId, extendId, deptId, buId, weixinUnionId, weixinWorkUserId, tenantCode
defaultOrg object fieldsdefaultOrg.orgId, defaultOrg.deptId, defaultOrg.companyId, defaultOrg.extendId

Replacement behavior:

  • A non-empty field value is replaced with a quoted string literal (e.g. #currentUser.userId# → '123456'); empty values are replaced with null.
  • When merging multiple rules (replaceRuleVariable(List<Permission>, User)), rules are deduplicated, whitespace-normalized, wrapped in parentheses, and joined with OR.
  • After replacement, any remaining #...# placeholder throws an exception (carrying entity name, original rule, and the placeholder list) — unresolved variables never reach a query.

Attachment Relation Classes​

UserOrg (user-org attachment, extends OrgCore)​

The membership relation between a user and an organization; one user may attach to multiple orgs.

AttributeTypeMeaning
(inherited)—orgId (attached org ID)/code/pid/name/tenantCode
fullNameStringFull org name (full path; filled from name by the enricher when empty)
deptIdStringParent department ID of this org (derived)
companyIdStringOwning company ID (derived)
extendIdStringCompany extension ID of the owning company (derived)
defaultOrgBooleanWhether this is the default org; true means this attachment is the user's default department
typeStringOrg type, same values as Org.type
categoryStringOrg category, see table below
descriptionStringDescription

Platform values of category (OrgCategoryEnum):

ValueMeaning
insideInternal
outsideExternal
virtualVirtual

UserRole (direct role, extends Role)​

A role attached directly to the user; no extra fields. The role is granted to the user without going through an org.

UserOrgRole (user-org role, extends Role)​

The user-org role contract model: a userId × orgId × roleId triple (userId is implicit when embedded in a User snapshot).

AttributeTypeMeaning
(inherited)—Role fields, see Role
orgIdStringSource org of the role (the org the role is attached to)

Semantics: the only way a department role takes effect for a user — the user is attached through this relation. The user does not have to be a member of the source org (membership is UserOrg, an independent relation that grants no role inheritance).

OrgRole (org-attached role, extends Role)​

The org-attached role contract model (a role attached to an org).

AttributeTypeMeaning
(inherited)—Role fields, see Role
orgIdStringThe org (department) the role is attached to

Semantics: the role is attached to an org (department) and provided by that department. Only direct departments take effect — no upward recursion along the tree. The attachment itself never grants the role to members automatically; for a user it takes effect only via a direct UserOrgRole.

UserRoles (aggregate of the two attachment results)​

AttributeTypeMeaning
userRolesList<UserRole>Direct roles
userOrgRolesList<UserOrgRole>Org-attached roles (department roles, orgId = source org)

getEffectiveRoles() shares the semantics of User.getEffectiveRoles(): direct ∪ org-attached, deduplicated by code.

Relation Rules​

  1. Org tree: Org nodes link through pid, empty at the root; type marks the node type. Relation resolution (department/company ownership) walks up the parent chain with a visited set guarding against cycles.
  2. User-org: many-to-many attachments (UserOrg), defaultOrg=true marks the default; when User.orgId is empty it is resolved from attachments (default org first, then the first attachment).
  3. Two role grant shapes: direct (UserRole) and department role (UserOrgRole, userId × orgId × roleId — the user need not be a member of that org). Both are user-side relations.
  4. Role-org attachment (OrgRole): a role attached to a department; only direct departments take effect, no recursion. The attachment never auto-grants members — user-side effect requires a direct UserOrgRole.
  5. Effective roles: direct ∪ org-attached, deduplicated by code, always taken from getEffectiveRoles().
  6. Company ownership: take the first ancestor with type=company along the parent chain, falling back to the top-level ancestor when none exists; companyId/companyName/extendId/buId/buName derive from it.
  7. Data permission effect: grouped by entity, the rule with the largest weight wins (getDataPermissionByEntity); multiple rules are merged with OR after variable replacement.
  8. System principal: systemPrincipal=true skips data-permission filtering but keeps tenant isolation — for scheduled jobs and other background scenarios.
  9. Delegation: the effective identity is the delegating user (written to creator/updater); delegateUserId/delegateUserName record the actual executor for audit only.

Summary​

  • The model layer is a pure data contract: entities (tenant / app / org / user / role / permission) + relation classes (org attachment and the three role attachment shapes), with no source details.
  • The user is the center: org- and company-ownership fields are all derived values filled by enrichers at loading; permission collections are not loaded by default (auth-center domain).
  • Effective-role semantics converge on getEffectiveRoles(): direct ∪ org-attached deduplicated by code; the only way a department role takes effect for a user is a direct UserOrgRole.
  • Data permissions take effect per entity by the largest weight; rule variables support a strict whitelist and unresolved placeholders hard-fail.
