Workflow Orchestration

This page describes the core model of geelato-workflow process design: process nodes, sequence flows, participants, process properties and node properties. The designer produces a JSON process definition; on save the workflow service converts it into standard BPMN 2.0 and deploys it to the engine. Integrators only need the business model and fields described here — no BPMN knowledge required.

For definition save/publish/version APIs see Define Integration; for runtime behavior see Workflow Runtime.

Definition Structure​

A process definition consists of three parts:

PartDescription
Process nodes (workflowNodes)Node list; must contain a start node and an end node
Sequence flows (sequenceFlows)Connections between nodes, at least one; they decide the routing
Process propertiesDefinition-level info: identifiers, name, group, form page, version status
{
  "defineKey": "leave_apply",
  "name": "Leave Application",
  "appId": "1001",
  "defineGroup": "HR",
  "pageId": "leave_form_page",
  "workflowNodes": [
    { "id": "start_1", "name": "Start", "nodeType": "start", "properties": [] },
    { "id": "initiate_1", "name": "Apply", "nodeType": "initiate", "properties": [] },
    { "id": "audit_1", "name": "Manager Approval", "nodeType": "audit", "properties": [
        { "name": "assignee", "value": [{ "assignType": "role", "assignObject": "dept_manager" }] },
        { "name": "auditType", "value": "any" }
      ] },
    { "id": "end_1", "name": "End", "nodeType": "end", "properties": [] }
  ],
  "sequenceFlows": [
    { "id": "flow_1", "sourceRef": "start_1", "targetRef": "initiate_1", "isAgree": 1 },
    { "id": "flow_2", "name": "Agree", "sourceRef": "initiate_1", "targetRef": "audit_1", "isAgree": 1 },
    { "id": "flow_3", "name": "Pass", "sourceRef": "audit_1", "targetRef": "end_1", "isAgree": 1 }
  ]
}

Process Nodes​

A node is a processing step in the process. Each node has these fields:

FieldTypeDescription
idstringNode identifier, unique within the definition; sequence flows reference nodes by it
namestringNode name (2-50 characters)
nodeTypestringNode type, see table below
propertiesarrayNode property list ({name, value} pairs), see Process Node Properties
x / y / width / heightnumberCanvas layout (persisted by the designer, may be empty)

Node Types​

TypeNameBehavior
startStartVirtual node; the process entry. Exactly one per definition
endEndVirtual node; the process exit. Reaching it completes the process normally
initiateInitiateFirst node reached after the process starts; the initiator is bound as handler and a draft pending task is created
auditAuditApprover gives an agree/deny conclusion; executed as parallel multi-instance, multiple approvers judged by the completion rule
handleHandleHandling user task; with a configured participant the handler is resolved at runtime, otherwise any user with permission may handle it
noticeNoticeAutomatic: sends notifications per node config and flows on; produces no pending task
serviceServiceAutomatic: runs a script or HTTP call and flows on; produces no pending task
exclusiveGatewayExclusive gatewayPicks one outgoing flow by condition evaluation
parallelGatewayParallel gatewayForks multiple branches; at join, waits for all branches
hqCountersignMulti-person parallel voting approval node; node conclusion judged by completion rule and reject strategy
countersignStart / countersignEndCountersign start/end (legacy)Legacy countersign model, kept for backward compatibility only; use hq for new definitions

:::note Fallback for automatic nodes When a notice or service node fails, the engine automatically creates a manual fallback task (handler = initiator). The handler can choose re-run (loop back and re-run the failed node) or skip (skip the failed node and flow to its original downstream). :::

Sequence Flows​

A sequence flow connects two nodes and decides the routing:

FieldTypeDescription
idstringFlow identifier
namestringFlow name (e.g. "Agree" / "Deny"; shown in next-step selection and path text)
sourceRefstringSource node id
targetRefstringTarget node id
conditionExpressionstringCondition expression evaluated against form data / process variables; exclusive gateway outgoing flows must have one
isAgreeintWhether this is an agree-type flow: 1 agree line, 0 deny line

Routing rules:

  • Agree / deny lines: when submitting from an audit or countersign node, outgoing flows are filtered by the conclusion (isAgree) — agree follows isAgree=1 lines, deny follows isAgree=0 lines.
  • Condition lines: conditionExpression is evaluated against process variables (including form data); typical use is an exclusive gateway with multiple outgoing flows selected by business data.
  • Default routing: flows without a condition, or with a true condition, participate in routing. If no exclusive gateway condition matches, the process errors — conditions should be complete at design time.
  • Parallel routing: after a parallel gateway fork, all outgoing flows take effect; at join, all branches must arrive.

Participants​

User task nodes (audit / handle / hq) configure participants via the assignee property; multiple entries can be combined.

Assignee Configuration​

FieldDescription
assignTypeParticipant type: user specified users, role roles, dept departments, dept_role dept-role (orgId:roleId), initiator the initiator
assignObjectParticipant identifiers, multiple values comma-separated (user ids or role ids)
withChildInclude sub-departments; only effective for assignType=dept

Runtime semantics per type:

assignTypeassignObject meaningResolution
userUser id listThe specified users
roleRole id listAll users under the roles
deptDepartment id listAll users in the departments; withChild=true includes sub-departments
dept_roledeptId:roleId listUsers in the department holding the role
initiatorNot neededThe process initiator (used as fallback handler for automatic nodes and notice recipients)

Resolution Timing​

  • Pick at submit: before submitting, resolve candidate handlers (StepUser) via the next-step and participant resolution APIs and let the submitter confirm; whether the target node requires picking is marked by needAssignee.
  • Fallback resolution: at submit time, for audit/countersign target nodes without explicitly picked users, the engine resolves participants from the node assignee config; when the result is empty the node's emptyAssigneeStrategy applies (see Empty Participant Strategy).

Assignee Limit​

assigneeLimit caps the number of participants: 0 unlimited, positive integer N at most N people. When resolved candidates exceed the limit, the submitter must trim before submitting.

Empty Participant Strategy​

emptyAssigneeStrategy decides the behavior when no participant can be resolved for the target node:

ValueBehavior
initiatorDefault. The process initiator acts as handler, avoiding a stuck process
skipThe node is reached with an empty participant set, completes immediately and flows on
errorSubmission fails with an error saying the node has no configured approver

Process Properties​

Process properties are definition-level info saved with the definition JSON:

FieldRequiredDescription
defineKeyRequired on updateUnique definition identifier (generated on first create); versions evolve under the same key
nameYesProcess name
remarkNoRemark
appIdYesOwning application id, used to filter definitions and tasks by application
defineGroupNoProcess group (for list filtering)
pageIdNoBound form page id; start/handle pages load the business form (iframe) from it
sourceNoDesigner layout raw data (maintained by the front end)
lockVersionNoOptimistic-lock baseline; validated on save to detect concurrent edits

Versions and Status​

Definitions evolve by version under the same defineKey. Version status:

StatusDescription
designDraft: editable, not deployed to the engine
debugDebug: produced by debug deploy; runnable only by debug-start APIs, for pre-release validation
activatedActivated: published; formal start APIs run this version
historyHistory: superseded by a newer publication; running instances keep executing the original version

Deploy actions (publish, debug deploy, batch deploy) and edit locks are documented in Define Integration.

Countersign Rule Properties (audit / hq)​

Countersign nodes run as parallel multi-instance: multiple people hold pending tasks simultaneously, and the node conclusion is judged by completion rule and reject strategy:

namevalue valuesDefault
completionRuleall all must agree; any any one agree; ratio by percentage (with completionValue as the numerator, positive integer); count by votes (with completionValue as vote threshold, positive integer)all
completionValueNumerator for ratio (e.g. 60 means 60%) or vote threshold for count—
rejectStrategyveto_any any single denial rolls back; vote_all collect all votes then judgeveto_any
emptyAssigneeStrategyinitiator / skip / error, see Empty Participant Strategyinitiator

:::note auditType vs completionRule auditType=any/all is the simplified form of the approval mode, internally mapped to completion rules any/all; an explicit completionRule takes precedence over auditType. Use completionRule + completionValue for ratio- or vote-based control. :::

Grouped Countersign Properties (hq)​

Grouped countersign splits participants into groups; each group participates in the countersign as one opinion body:

namevalue valuesDefault
groupSourcedept group by department (incl. sub-departments); role group by role; custom explicit groups (with groups); empty = no grouping, plain countersignempty
groupInnerRuleall group agrees only when all members agree; any one agreeing member makes the group agreeall
countingUnitmember count by person; group count by group (completion rule counts group conclusions)member
groupKeyNameGroup name display template (e.g. {dept} Countersign)—
groupsExplicit groups when groupSource=custom: [{key, name, members: [userId]}]—

Empty groups are skipped automatically (marked skipped) and excluded from group-level counting; when all groups are empty, emptyAssigneeStrategy applies. Countersign progress (incl. group progress) is queried via the instance detail / countersign progress APIs, see Runtime Integration · Common Response Structures.

Automatic Node Properties (notice / service)​

nameDescription
noticeConfigNode notification config: template, recipients, etc.; the engine sends notifications on node arrival/completion
asyncWhether the automatic node runs asynchronously: true async (requires the async executor); synchronous by default

Button Reference​

GET /api/define/getButtonMeta returns the button metadata supported by the system; the designer renders configurable buttons from it and the runtime filters by node type. The submit button is not part of node configuration (injected automatically by the runtime depending on whether the node needs an approval conclusion).

ButtonTextDefault saveDefault shown on node typesLevel
wf_btn_agreeAgreesaveaudit / hqprimary
wf_btn_denyDenynoaudit / hqprimary
wf_btn_back_previousReturn to previousnoaudit / handlesecondary
wf_btn_back_originReturn to initiatornoaudit / handlesecondary
wf_btn_back_anyReturn to any nodenoaudit / handlesecondary
wf_btn_stageSave draftsaveinitiate / audit / handle / hqspecial
wf_btn_addsignAdd signernoaudit / hqsecondary

wf_btn_circulateCirculatenoaudit / handle / hq / notice / endspecial
wf_btn_attachUpload attachmentnoall user task nodessecondary

Levels: primary main action in the action area; special special buttons (top-right of form/process info); secondary secondary buttons (more actions).

:::note Withdraw and remind Withdraw and remind are page-level buttons, not part of node button config: their visibility is decided by the current user's relation to the instance (initiator, pending task, etc.). :::

Return-type buttons (return to previous / initiator / any node) are not available on countersign nodes — countersign nodes can only flow forward, return is not supported.
