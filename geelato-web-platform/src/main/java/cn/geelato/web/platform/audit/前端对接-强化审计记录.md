# 审计日志前端对接文档：如何强化审计记录

> 本文档只讲一件事：**前端在发起写操作时，如何通过请求头声明业务意图，让审计日志更准确、更可读。**
>
> 不涉及查询接口。

---

## 一、为什么需要前端配合

平台审计日志由后端自动记录，分两层：

1. **注解层**：后端开发者在业务方法上挂 `@AuditLog` 注解，能准确识别"审批运单""提交申请"等动作。
2. **ORM 兜底层**：所有写操作自动记录，靠元数据中文化。

**问题出在哪？**

大量业务操作走的是**通用 CRUD / 低代码 / MQL 接口**（如 `PUT /orders/{id}`）。这类接口到后端时，已经分不清这是"审批通过"还是"仅仅是改了个收货人电话"。后端只能产出**弱语义兜底记录**：

> 张三 修改了 运单 WBL-2024-001（2个字段：状态、金额）

而理想的可读记录应该是：

> 张三 审批了 运单 WBL-2024-001，状态 待审批→已通过，金额 100→200

**前端的作用**：在发起有明确业务含义的写操作时，通过 HTTP 请求头把"这是什么操作"告诉后端，审计记录就能从弱语义升级为准确的业务摘要。

---

## 二、什么时候需要前端传

| 操作类型 | 前端是否需传 | 举例 |
|---|---|---|
| 纯字段编辑（无业务动作含义） | ❌ 不用传 | 表单里改个收货人电话、备注 |
| 有明确业务含义的动作 | ✅ **要传** | 审批、提交、作废、确认、发布、撤销、驳回 |
| 后端已挂 `@AuditLog` 注解的接口 | ❌ 不用传 | 后端已自行声明（问后端开发者确认） |

**判断口诀**：这个按钮点下去，是"做了一件业务上的事"（要传），还是"只是改了几个字段"（不用传）。

---

## 三、请求头参数表

前端通过以下 HTTP 请求头声明业务意图：

| 请求头 | 说明 | 示例 | 必填 |
|---|---|---|---|
| `X-Audit-Operation` | **业务动作名**（中文，"动词+对象"格式） | `审批运单` | ✅ 核心必传 |
| `X-Audit-Biz-Type` | 业务类型标识（英文，与后端约定） | `freight_order` | 否 |
| `X-Audit-Target-Id` | 业务对象主键 | `a1b2c3d4` | 否（能传更好） |
| `X-Trace-Id` | 链路追踪ID | `7f8e9d...` | 否 |

### 字段取值规范

- **`X-Audit-Operation`（最重要）**
  - 格式：`动词 + 业务对象`，如 `审批运单`、`提交申请单`、`作废合同`、`发布商品`
  - **不要只写动词**：`审批` ❌（审计会变成"张三 审批了 运单 xxx"，缺少对象感）→ `审批运单` ✅
  - **不要写英文**：`approve_order` ❌ → `审批运单` ✅
  - 用中文，因为这是直接展示给用户看的

- **`X-Audit-Biz-Type`**
  - 业务模块的英文标识，与后端约定（如 `freight_order`、`contract`、`leave_apply`）
  - 用于按业务类型归类、查时间线
  - 不传时后端用实体名兜底

- **`X-Audit-Target-Id`**
  - 被操作的业务对象主键（通常是记录的 id）
  - 传了能让审计更精准地关联到具体对象
  - 不传时后端从请求体/路径推断

## 四、如何传递

### 方式 A：单请求按需传（推荐 ✅）

在点击具体业务按钮时，给该请求单独加 header。**最精准，不污染其他请求。**

**Vue3 + axios 示例：**

```js
// 审批运单
function approveOrder(orderId) {
  return axios.put(`/api/orders/${orderId}/status`, 
    { status: 'confirmed' },
    {
      headers: {
        'X-Audit-Operation': '审批运单',
        'X-Audit-Biz-Type': 'freight_order',
        'X-Audit-Target-Id': orderId,
      }
    }
  );
}

// 作废合同
function cancelContract(contractId) {
  return axios.post(`/api/contracts/${contractId}/cancel`, 
    { reason: '客户取消' },
    {
      headers: {
        'X-Audit-Operation': '作废合同',
        'X-Audit-Biz-Type': 'contract',
        'X-Audit-Target-Id': contractId,
      }
    }
  );
}
```

**fetch 示例：**

```js
async function approveOrder(orderId) {
  await fetch(`/api/orders/${orderId}/status`, {
    method: 'PUT',
    headers: {
      'Content-Type': 'application/json',
      'X-Audit-Operation': '审批运单',
      'X-Audit-Biz-Type': 'freight_order',
      'X-Audit-Target-Id': orderId,
    },
    body: JSON.stringify({ status: 'confirmed' }),
  });
}
```

### 方式 B：axios 拦截器动态注入（适合页面级）

当某个页面/模块的操作都有统一业务含义时，可在请求拦截器里根据上下文动态注入：

```js
// 用一个模块级的 ref/current 变量记录"当前页面正在执行的业务动作"
const currentAuditOperation = ref(null);

axios.interceptors.request.use((config) => {
  if (currentAuditOperation.value) {
    config.headers['X-Audit-Operation'] = currentAuditOperation.value.operName;
    config.headers['X-Audit-Biz-Type'] = currentAuditOperation.value.bizType;
    config.headers['X-Audit-Target-Id'] = currentAuditOperation.value.targetId;
  }
  return config;
});

// 触发审批前设置，完成后清除
async function handleApprove(order) {
  currentAuditOperation.value = {
    operName: '审批运单',
    bizType: 'freight_order',
    targetId: order.id,
  };
  try {
    await approveOrderApi(order.id);
  } finally {
    currentAuditOperation.value = null; // ⚠️ 务必清除，避免污染后续请求
  }
}
```

> ⚠️ **使用拦截器方式时，务必在请求完成后清除标记**（finally 里置 null），否则后续无关请求也会被错误地打上业务标签。

## 五、传与不传的效果对比

同一个"审批运单"操作：

| | 审计记录摘要 |
|---|---|
| ❌ **没传**（兜底层自动记录） | `张三 修改了 运单 WBL-2024-001（2个字段：状态、金额）` |
| ✅ **传了 `X-Audit-Operation: 审批运单`** | `张三 审批了 运单 WBL-2024-001，状态 待审批→已通过，金额 100→200` |

差别：
- 没传 → 只知道"改了2个字段"，看不出业务意图（可能是审批，也可能是误操作改状态）
- 传了 → 清楚知道"这是一次审批动作"，且字段变化已中文化展示

## 六、最佳实践与注意事项

1. **`X-Audit-Operation` 用"动词+对象"**
   - ✅ `审批运单`、`提交申请单`、`作废合同`、`发布商品`、`驳回退款`
   - ❌ `审批`（缺对象）、`approve`（非中文）、`order_approve`（非中文）

2. **一个页面多个动作按钮，各自传各自的 operName**
   - 列表页有"审批""驳回""作废"三个按钮 → 点击哪个，该请求就传对应的 operName，不要混用

3. **只在写操作传**（POST / PUT / DELETE）
   - 查询（GET）接口不需要传，传了也无意义

4. **不传不会报错**
   - 不传时后端走兜底层，记录仍可读（中文化），只是语义弱、分不清具体业务动作
   - 所以这是"锦上添花"，但为了审计质量，关键业务动作请务必传

5. **与后端确认是否已有注解**
   - 如果某个接口后端已挂 `@AuditLog` 注解，前端就不用再传（避免重复/冲突）
   - 不确定时问后端开发者：这个接口有没有 `@AuditLog`？

6. **委托代办场景无需特殊处理**
   - "代客操作"的身份信息（谁代替谁操作）由后端从登录会话自动获取，前端无需传任何额外参数

## 附：完整请求示例

```http
PUT /api/orders/a1b2c3d4/status HTTP/1.1
Host: app.example.com
Content-Type: application/json
Authorization: JWTBearer xxx
X-Audit-Operation: 审批运单
X-Audit-Biz-Type: freight_order
X-Audit-Target-Id: a1b2c3d4

{"status":"confirmed","comment":"同意"}
```

后端将记录：

> **张三** 审批了 运单 **WBL-2024-001**，状态 待审批→已通过，金额 100→200
> （如当时是代客操作，还会标注"代李四"）
